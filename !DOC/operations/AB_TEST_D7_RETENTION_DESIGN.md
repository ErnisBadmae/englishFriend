# Проект A/B-теста: удержание на 7-й день

Документ, по которому эксперимент запускается, а не обсуждается. Все решения приняты
до старта — в этом и смысл: после старта менять правила нельзя, иначе результат
не интерпретируется.

Статус: **спроектирован, не запущен.**

## 1. Гипотеза и что именно меняем

Формулировка гипотезы обязана быть проверяемой, то есть содержать метрику, направление
и величину.

> Напоминание о серии («streak at risk») вечером шестого дня повышает удержание
> на 7-й день у новых пользователей не менее чем на 5 процентных пунктов.

Почему выбрано это воздействие:

- **дёшево и изолированно** — не трогает обучающий контур, только уведомление;
- **атрибутируемо** — если метрика сдвинется, объяснение однозначно;
- **опирается на уже существующие поля** — `users.current_streak` и
  `users.last_activity_date` есть в схеме, считать ничего нового не надо.

Альтернативы, которые сознательно отклонены на этот раз: изменение онбординга (влияет
на всю воронку, эффект размажется) и смена модели генерации (меняет качество ответов,
то есть смешивает два эффекта сразу).

## 2. Метрика

**Основная (единственная, по которой принимается решение):**

> Доля новых пользователей, у которых есть хотя бы одна сессия в интервале
> `[created_at + 7 дней, created_at + 8 дней)`.

```sql
WITH cohort AS (
    SELECT u.id, u.created_at, a.variant
    FROM users u
    JOIN experiment_assignments a ON a.user_id = u.id
    WHERE a.experiment = 'd7_streak_nudge'
      AND u.deleted_at IS NULL
      AND u.created_at < :enrollment_end          -- набор закрыт
      AND u.created_at + INTERVAL '8 days' <= now()  -- когорта дозрела
)
SELECT c.variant,
       COUNT(*)                                   AS users,
       COUNT(*) FILTER (WHERE s.user_id IS NOT NULL) AS retained,
       ROUND(100.0 * COUNT(*) FILTER (WHERE s.user_id IS NOT NULL) / COUNT(*), 2) AS d7_pct
FROM cohort c
LEFT JOIN LATERAL (
    SELECT 1 AS user_id FROM sessions s
    WHERE s.user_id = c.id
      AND s.started_at >= c.created_at + INTERVAL '7 days'
      AND s.started_at <  c.created_at + INTERVAL '8 days'
    LIMIT 1
) s ON TRUE
GROUP BY c.variant;
```

Две детали в этом запросе принципиальны и обе — про честность замера.

**`created_at + 8 days <= now()`** — в расчёт попадают только **дозревшие** когорты.
Без этого условия вчерашние регистрации войдут в знаменатель с гарантированным нулём
в числителе и занизят обе группы, причём неравномерно, если набор шёл неравномерно.

**Окно ровно в сутки, а не «был активен за первую неделю».** Узкое окно строже, но
шумнее. Если инфлюкс новых пользователей не позволяет набрать выборку (см. §4),
допустимо перейти к определению «хотя бы одна сессия в дни 5–7» — оно чувствительнее
при том же размере. **Определение выбирается один раз до старта и не меняется.**

**Вспомогательные (смотрим, решение по ним не принимаем):** число сессий на
пользователя за 7 дней, медианная длина сессии, доля дошедших до конца сценария.

**Guardrail-метрики (ухудшение = остановка эксперимента):** p95 времени голосового
ответа, доля ошибок, доля отписок от уведомлений, стоимость на сессию.

Доля отписок здесь не формальность: воздействие — это push, и самый вероятный вред
именно такой — метрика удержания выросла, а часть людей выключила уведомления навсегда.

## 3. Единица рандомизации и разбиение

**Единица — пользователь** (`users.id`), не сессия и не устройство. Сессии одного
человека зависимы, разбиение по ним занизит дисперсию и даст оптимистичный p-value.

**Кто попадает в эксперимент: только новые пользователи**, зарегистрированные после
старта. Удержание на 7-й день — метрика жизненного цикла, отсчитываемая от регистрации;
у существующих пользователей их седьмой день давно позади, включить их нельзя.

**Назначение детерминированное и персистентное:**

```sql
CREATE TABLE experiment_assignments (
    experiment   TEXT        NOT NULL,
    user_id      BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    variant      TEXT        NOT NULL CHECK (variant IN ('control', 'treatment')),
    assigned_at  TIMESTAMP   NOT NULL DEFAULT now(),
    PRIMARY KEY (experiment, user_id)
);
```

Вариант вычисляется как `hash(experiment_salt || user_id) % 2` и **записывается**.
Хэш — чтобы назначение не зависело от порядка и переживало перезапуск; запись —
чтобы результат можно было перепроверить задним числом, а не пересчитывать хэш
той же версией кода.

Соль своя на каждый эксперимент: иначе пользователь, попавший в `treatment` однажды,
будет туда попадать всегда, и эксперименты станут коррелированными.

Деление **50/50** — при фиксированном общем размере это даёт максимальную мощность.

## 4. Размер выборки и длительность

Базовый уровень принимается `p₀ = 0.27` (значение из текущей отчётности; **до старта
обязательно перепроверить по факту** — если реальное удержание другое, все числа ниже
пересчитываются).

При `α = 0.05` (двусторонний) и мощности `0.8`:

| MDE | на группу | всего |
|---|---|---|
| 8.0 пп (27% → 35%) | 484 | **968** |
| 5.0 пп (27% → 32%) | 1 238 | **2 476** |
| 3.0 пп | 3 438 | **6 876** |
| 2.0 пп | 7 736 | **15 472** |

Округление только вверх и до чётного итога: дробного участника не бывает, а нечётный
total несовместим с делением 50/50.

**Перед запуском размер пересчитать библиотекой.** Формула ниже — приближение по
дисперсии базового уровня; строгий расчёт для двух долей использует объединённую
дисперсию при нулевой гипотезе и раздельную при альтернативе
(`statsmodels.stats.proportion.power_proportions_2indep`). Таблица годится для решения
«ставить или не ставить», но не как окончательное число участников.

Формула: `n = 2·(z₁₋α/₂ + z₁₋β)²·p₀(1−p₀) / Δ²`, то есть примерно `16·p(1−p)/Δ²`
на группу для этих α и мощности.

**Из таблицы следует главное решение проекта.** Чувствительность стоит дорого:
уменьшение MDE вдвое учетверяет выборку. Поэтому MDE выбирается **не из желания
поймать любой эффект, а из того, какой эффект окупает разработку и поддержку**.
Для уведомления, которое пишется за день, разумный порог — 5 пп.

**Длительность считается так:**

```
дней набора = 2 · n_на_группу / (новых пользователей в день)
общая длительность = дни набора + 7 дней дозревания последней когорты + 1 день
```

Семь дней дозревания — та часть, которую забывают чаще всего: последний
зарегистрированный участник должен прожить свои семь дней, прежде чем его можно
посчитать.

**Проверка выполнимости перед стартом.** Если приток новых пользователей — `N` в день,
то на MDE 5 пп нужно `2476/N` дней набора. При 30 новых в день это 83 дня плюс неделя,
то есть три месяца. **Если срок получается неприемлемым, честный вывод — эксперимент
на этой метрике при этом масштабе не ставится**, и надо либо брать более
чувствительную метрику (доля активных в дни 5–7 вместо ровно седьмого дня), либо
принимать больший MDE, либо не ставить эксперимент вовсе. Признать невыполнимость
до старта — нормальный результат проектирования; обнаружить её после — потерянный
квартал.

## 5. Процедура

**Шаг 0. A/A-тест.** Перед экспериментом неделя с назначением вариантов, но без
различий в поведении. Ожидание: `p > 0.05` и близкие доли. Значимая разница в A/A
означает поломку разбиения, метрики или запроса — и до её починки A/B бессмысленен.

**Шаг 1. Набор.** Идёт до достижения расчётного размера или до заранее объявленной
даты — что наступит раньше. Дата фиксируется в этом документе до старта.

**Шаг 2. Дозревание.** Семь дней после закрытия набора. Метрику в это время **не
смотрим**.

**Шаг 3. Анализ. Один раз.**

- двусторонний z-тест для двух долей (или точный критерий Фишера при малых числах);
- **доверительный интервал для разности долей — важнее p-value**: он показывает
  и направление, и масштаб, и позволяет отличить «эффекта нет» от «не хватило данных»;
- проверка sample ratio mismatch: если фактическое деление далеко от 50/50, разбиение
  сломано и результат недействителен независимо от p-value.

**Шаг 4. Решение** принимается по совокупности: значимость, нижняя граница
доверительного интервала выше порога окупаемости, guardrail-метрики не ухудшились.

## 6. Что запрещено во время эксперимента

- **Подглядывать и останавливаться по достижении `p < 0.05`.** Каждая проверка — ещё
  один шанс случайно пересечь порог; при ежедневных проверках ложноположительный
  результат практически гарантирован. Нужен промежуточный контроль — заранее
  заложить последовательный критерий с распределением α, а не смотреть «просто так».
- **Менять воздействие или метрику после старта.**
- **Добавлять метрики и объявлять значимой ту, что «выстрелила».** Основная метрика
  одна и названа в §2; остальные — описательные. Проверив 20 метрик при α = 0.05,
  одну «значимую» получаешь просто так.
- **Выкатывать другие изменения в тот же контур.** Иначе эффекты смешаются.

## 7. Известные ограничения — записать до старта

- **Эффект новизны.** Первые дни реакция на любое новое уведомление завышена. При
  коротком эксперименте эффект может быть переоценён; проверяется повторным замером
  через месяц.
- **Сетевых эффектов нет** — пользователи между собой не связаны, поэтому переноса
  воздействия между группами не ожидается. Для продукта с социальными функциями это
  предположение надо было бы проверять.
- **Один канал.** Все пользователи в Telegram (`primary_channel`), поэтому переноса
  на другие каналы вывод не имеет.
- **Удержание на 7-й день — прокси.** Оно не гарантирует удержания на 30-й и тем более
  выручки. Улучшение D7 push-уведомлением исторически часто не переносится на D30.

## 8. Что считать результатом

Любой из трёх исходов является результатом и записывается:

1. **Эффект есть и окупается** — выкатываем на всех.
2. **Эффект статистически значим, но нижняя граница интервала ниже порога
   окупаемости** — не выкатываем, фиксируем размер эффекта.
3. **Эффект не обнаружен** — фиксируем **верхнюю границу** доверительного интервала.
   Это ценная информация: «эффект, если он есть, не больше стольких-то пунктов» —
   гораздо содержательнее, чем «не подтвердилось».
